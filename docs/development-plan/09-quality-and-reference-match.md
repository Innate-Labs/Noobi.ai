# 阶段 09：参考对照、长流程与体验质量

状态：开发中（已有部分专项/样板，不代表整阶段已完成或已验收）。实际进度以 [STATUS.md](STATUS.md) 为准。

## 目标与入口条件

分别证明风格/玩法对齐、完整运行可靠性和玩家体验。

- 前置条件：阶段 08 已由用户验收通过；对应记录可在 STATUS.md 查到。
- 需求追踪：R07 R12，见 [REQUIREMENTS.md](REQUIREMENTS.md)。
- 开发前必读：[README.md](README.md)、[STANDARDS.md](STANDARDS.md)。
- 代码入口（需开工时核实）：gameplayExperienceEvaluator.ts、quality/、runtime/、评审输入、参考对照及报告 UI。拟新增服务名称不构成既有实现。

## 开发任务

- [ ] 09-D01：在相近镜头和游戏状态对照参考与产物，分别评估风格、镜头、动作、反馈和规则。
- [ ] 09-D02：结合状态断言、局部场景回归、长时间运行和正常起点全流程；扩展现有短试玩限制。
- [ ] 09-D03：固定设备/分辨率/图形档位，采集帧耗时、长帧、内存趋势、加载及错误。
- [ ] 09-D04：分开报告运行可靠性、需求完整度、视觉一致性与体验；引入真人试玩并修复阻断卡点。

## 本阶段开发标准

- 玩法靠实际行为验证，不能只看画面相似；VLM 评分不能等同玩家满意度。
- 参考中未展示的规则按已选方案验收；用户主动改编的部分不判作“参考不一致”。
- 验收标准在开发前冻结；实现、测试与用户体验同步完成。不得靠降低标准使阶段通过。
- 每个任务有实际代码/产物及证据；外部能力和真实模型验证与 mock 测试分开记录。

## 自动验证与真实运行验收

| 编号 | 检查 | 通过标准 |
|---|---|---|
| 09-A01 | 诊断准确性 | 预置遮挡、黑屏、碰撞错位、错误伤害、坏存档等失败样例，系统能定位对应证据。 |
| 09-A02 | 时间覆盖 | 当前构建完成全流程和连续至少 30 分钟稳定性运行；较长游戏覆盖其实际全流程。 |
| 09-A03 | 性能 | 报告参考设备、分辨率、档位及帧耗时分布；60 FPS 为正常档位目标，降档须显式记录。 |
| 09-A04 | 同一构建 | 报告、截图、试玩和发布候选 hash 一致；修复后重跑受影响测试。 |

代码变更完成后执行仓库要求的 `npm run verify`；涉及界面时执行 `npm run smoke:ui` 并实际检查截图。除此以外，执行上表要求的真实运行测试。命令、环境、退出码、日志位置、构建 ID 写入阶段报告；未运行必须写明，不预填通过。

## 用户验收步骤

验收前，开发者必须提供可运行版本、准确启动方式、示例输入/测试素材及下列操作所需的入口，不能只交代码 diff。

| 编号 | 你的操作 | 应看到的结果 |
|---|---|---|
| 09-U01 | 并排查看参考和实际作品 | 能逐项核对选定的风格/玩法特征以及主动改编内容。 |
| 09-U02 | 试玩并指出手感、节奏或难度问题 | 记录具体场景和问题，修复后提供前后对比。 |
| 09-U03 | 查看四类质量结论 | 不会出现以“基础运行 100 分”代替完整品质的结论。 |

## 交付物

对照报告、长流程录像/日志、性能报告、至少 3 名初始试玩者反馈及修复清单。

- 使用 [REPORT-TEMPLATE.md](REPORT-TEMPLATE.md) 建立 `reports/09-delivery.md`。
- 提供本阶段提交、运行/构建版本、日志与截图或录像链接、已知问题。
- 用户反馈后，将实际结论写入报告并更新 STATUS.md。

## 范围边界与风险

- 本阶段不做：不承诺机器能自动判定全部趣味；规模化用户评测在阶段 11。
- 风险处理：真人反馈或设备缺失时明确未验证，不能伪造测量数据；性能阈值在运行前冻结。

## 退出条件与汇报

所有开发任务与适用验收项有证据，开发者自验通过后状态改为“待用户验收”，立即向用户汇报本阶段做了什么、怎么试、验证结果和遗留问题。只有用户明确验收通过，才改为“已验收”并进入下一阶段。存在未完成项时留在本阶段；范围变更必须先由用户明确接受。

用户未回复、等待超时、测试全绿均不等于用户验收通过。禁止提前填写完成日期或用户意见。
