# 阶段 02：方案编辑、自带计划与变更方案

状态：未开始。实际进度以 [STATUS.md](STATUS.md) 为准。

## 目标与入口条件

用户能修改、组合或提交自己的计划；已有项目修改也先形成明确方案。

- 前置条件：阶段 01 已由用户验收通过；对应记录可在 STATUS.md 查到。
- 需求追踪：R03 R04，见 [REQUIREMENTS.md](REQUIREMENTS.md)。
- 开发前必读：[README.md](README.md)、[STANDARDS.md](STANDARDS.md)。
- 代码入口（需开工时核实）：阶段 01 方案服务、共享契约、方案编辑 UI、项目对话入口。拟新增服务名称不构成既有实现。

## 开发任务

- [ ] 02-D01：支持自然语言修改和结构化字段编辑：玩法、镜头、区域、角色、风格、平台、预算。
- [ ] 02-D02：支持粘贴或导入现有受支持的文本计划；保留明确要求，标记缺项与冲突。
- [ ] 02-D03：支持方案组合、版本历史、差异展示、锁定字段和取消未保存编辑。
- [ ] 02-D04：已有项目的变更方案说明修改范围、影响系统、存档兼容性及回归范围，并绑定当前项目版本。

## 本阶段开发标准

- 资料和导入文本视为需求数据，不能覆盖宿主规则。
- 修改范围可追踪；执行任务图与构建回退在阶段 05 加强，此阶段只完成方案契约和现有执行衔接。
- 验收标准在开发前冻结；实现、测试与用户体验同步完成。不得靠降低标准使阶段通过。
- 每个任务有实际代码/产物及证据；外部能力和真实模型验证与 mock 测试分开记录。

## 自动验证与真实运行验收

| 编号 | 检查 | 通过标准 |
|---|---|---|
| 02-A01 | 编辑保存 | 修改、重启、重新生成后字段保留；锁定字段不得被模型静默覆盖。 |
| 02-A02 | 冲突合并 | 平台、玩法或预算互斥时显示具体冲突，未解决前不能进入执行。 |
| 02-A03 | 自带计划 | 用户必需要求转换后仍有稳定 ID 和来源；导入中的指令不能改变宿主权限。 |
| 02-A04 | 增量方案 | 新增 Boss 等请求保留原项目需求；计划显示受影响测试与存档假设。 |

代码变更完成后执行仓库要求的 `npm run verify`；涉及界面时执行 `npm run smoke:ui` 并实际检查截图。除此以外，执行上表要求的真实运行测试。命令、环境、退出码、日志位置、构建 ID 写入阶段报告；未运行必须写明，不预填通过。

## 用户验收步骤

验收前，开发者必须提供可运行版本、准确启动方式、示例输入/测试素材及下列操作所需的入口，不能只交代码 diff。

| 编号 | 你的操作 | 应看到的结果 |
|---|---|---|
| 02-U01 | 修改 A，再要求加入 B 的部分玩法 | 可见合并结果和变化，保留手动设置。 |
| 02-U02 | 保存草稿并重启应用 | 编辑后的版本仍在，选中版本不漂移。 |
| 02-U03 | 上传自己的计划并提出局部修改 | 系统按用户计划整理，展示明确差异和缺项。 |

## 交付物

编辑与导入界面、版本差异、字段保护、已有项目变更方案示例。

- 使用 [REPORT-TEMPLATE.md](REPORT-TEMPLATE.md) 建立 `reports/02-delivery.md`。
- 提供本阶段提交、运行/构建版本、日志与截图或录像链接、已知问题。
- 用户反馈后，将实际结论写入报告并更新 STATUS.md。

## 范围边界与风险

- 本阶段不做：不建设大型可视化关卡编辑器，不在此阶段承诺完整资产/构建回退。
- 风险处理：正在执行的方案不可原地改写；新编辑形成下一版本并明确何时生效。

## 退出条件与汇报

所有开发任务与适用验收项有证据，开发者自验通过后状态改为“待用户验收”，立即向用户汇报本阶段做了什么、怎么试、验证结果和遗留问题。只有用户明确验收通过，才改为“已验收”并进入下一阶段。存在未完成项时留在本阶段；范围变更必须先由用户明确接受。

用户未回复、等待超时、测试全绿均不等于用户验收通过。禁止提前填写完成日期或用户意见。
