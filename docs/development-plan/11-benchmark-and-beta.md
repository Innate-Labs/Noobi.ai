# 阶段 11：多作品验证与首版验收

状态：未开始。实际进度以 [STATUS.md](STATUS.md) 为准。

## 目标与入口条件

证明能力可重复，并给出支持范围、成功率、成本和已知局限。

- 前置条件：阶段 10 已由用户验收通过；对应记录可在 STATUS.md 查到。
- 需求追踪：R14，见 [REQUIREMENTS.md](REQUIREMENTS.md)。
- 开发前必读：[README.md](README.md)、[STANDARDS.md](STANDARDS.md)。
- 代码入口（需开工时核实）：benchmarks/、评测执行器、制作与成本记录、发布说明。拟新增服务名称不构成既有实现。

## 开发任务

- [ ] 11-D01：固定 10 个支持范围内需求，每个独立运行 3 次；包含文字、截图、短视频和用户修改场景。
- [ ] 11-D02：标记开发集与留出需求；冻结模型、组件、预算、环境和成功判据，保留所有失败记录。
- [ ] 11-D03：至少交付三个主题/布局/机制组合不同的完整作品，分别走正式交付验收。
- [ ] 11-D04：邀请 8–12 名目标用户开展探索性试玩，整理上手、卡点、继续游玩意愿与需求偏差。

## 本阶段开发标准

- 自主成功必须未人工编辑生成工程且全部必需验收通过；人工补救单独分类。
- 目标为至少 24/30 次完整成功，属于首版试运行门槛而非泛化保证；未达标不改分母。
- 验收标准在开发前冻结；实现、测试与用户体验同步完成。不得靠降低标准使阶段通过。
- 每个任务有实际代码/产物及证据；外部能力和真实模型验证与 mock 测试分开记录。

## 自动验证与真实运行验收

| 编号 | 检查 | 通过标准 |
|---|---|---|
| 11-A01 | 基准可追踪 | 每次运行有需求、方案、参考、版本、预算、成本、结果和人工介入记录。 |
| 11-A02 | 失败可审计 | 失败与重试计入成本；无预算或外部条件导致未执行的任务不能记为通过。 |
| 11-A03 | 发布稳定性 | 无已知阻止流程或存档丢失的问题；所有宣布支持的平台有阶段 10 证据。 |
| 11-A04 | 回归保护 | 新生成需求和新版本未破坏之前标杆；完整交付率与分场景结果公开列明。 |

代码变更完成后执行仓库要求的 `npm run verify`；涉及界面时执行 `npm run smoke:ui` 并实际检查截图。除此以外，执行上表要求的真实运行测试。命令、环境、退出码、日志位置、构建 ID 写入阶段报告；未运行必须写明，不预填通过。

## 用户验收步骤

验收前，开发者必须提供可运行版本、准确启动方式、示例输入/测试素材及下列操作所需的入口，不能只交代码 diff。

| 编号 | 你的操作 | 应看到的结果 |
|---|---|---|
| 11-U01 | 随机挑选三个不同作品直接游玩 | 能正常启动并展现不同内容和选定玩法。 |
| 11-U02 | 抽查成功与失败记录 | 过程可追溯，没有隐藏人工代写或只展示成功样例。 |
| 11-U03 | 审阅支持范围、成本和体验报告 | 明确首版能做什么、限制是什么，决定是否接受首版。 |

## 交付物

30 次运行明细、至少三个成品、真人试玩记录、成功率/成本报告与首版说明。

- 使用 [REPORT-TEMPLATE.md](REPORT-TEMPLATE.md) 建立 `reports/11-delivery.md`。
- 提供本阶段提交、运行/构建版本、日志与截图或录像链接、已知问题。
- 用户反馈后，将实际结论写入报告并更新 STATUS.md。

## 范围边界与风险

- 本阶段不做：不以首版结果宣称任意游戏自动生成，不自动启动新品类扩展。
- 风险处理：本阶段消耗较高，执行前列出并确认具体模型/素材预算；预算不足保留未执行状态，不补写结果。

## 退出条件与汇报

所有开发任务与适用验收项有证据，开发者自验通过后状态改为“待用户验收”，立即向用户汇报本阶段做了什么、怎么试、验证结果和遗留问题。只有用户明确验收通过，才改为“已验收”并进入下一阶段。存在未完成项时留在本阶段；范围变更必须先由用户明确接受。

用户未回复、等待超时、测试全绿均不等于用户验收通过。禁止提前填写完成日期或用户意见。
