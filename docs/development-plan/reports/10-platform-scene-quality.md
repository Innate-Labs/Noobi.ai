# Noobi 平台专项：全场景资产覆盖与代表性 3D 场景验收

日期：2026-09-25。状态：开发者自验完成，待用户验收。

## 冻结范围

用户明确要求继续推进本专项。对应剩余清单 R09–R14、R25、R28 的场景检查部分，修改 Noobi 平台，不修改用户现有游戏。

基线 `58975ce5d0c8a7a12613d7ee3541bf595e0df274`，沿用 `codex/stage-01-plan-selection` 工作树，保留此前未提交修改。主制作链为图片参考 → Three.js 程序建模 → GLB → Godot。

交付目标：Godot 3D 运行时场景清单；包含程序生成地形、植被和实例网格的覆盖核对；采样缺失、超限、错误绑定与碰撞/交互证据不足不能通过；代表性场景必须在内容扩展前接受真实输入、截图和独立只读审查，最终构建重新检查。自动技术核对不声称美术质量已通过。

## 预先确定的验收标准

- S01：运行场景中未登记的几何对象被发现，不能通过增加账本模型数量掩盖缺失。
- S02：相机外对象仍计入清单；超过探针容量明确报不完整，不能静默截断并判通过。
- S03：模型资源、程序几何、实例对象、碰撞结构有实际运行证据；只有名称或声明不够。
- S04：代表性场景至少两个真实操作视角，并有碰撞接触和交互状态变化证据；缺失即修复。
- S05：3D 样板门槛接入生产顺序，未通过不扩展内容；最终交付重新核对当前冻结构建。
- S06：工程清单、运行证据及审查结论绑定构建；旧记录不验证新源码。
- S07：界面分开显示场景覆盖、证据缺口与待人工/独立审查状态，不展示虚假的综合质量分数。
- S08：使用隔离 Godot 3D 样例验证正确场景及故意遗漏、缺碰撞、采样超限等失败样例；使用真实引擎与浏览器输入，不修改真实用户游戏。

验证要求：必要单元与生产调度回归、`npm run verify`、完整应用截图、真实 Godot 场景采样与输入运行。模型审查调用与无模型测试分开记录；未运行的部分明确注明。

## 本轮实现

1. `.noobi/scene-quality.json` 描述风格、色板、比例、灯光、代表性场景、全部目标场景、对象绑定、外观设计、碰撞意图和对应试玩步骤。绑定区分实际模型、程序几何、HUD 和第一人称视点；模型可声明一个或多个资源，以覆盖角色与装备组合。
2. 宿主运行探针独立扫描 SceneTree，不依赖 Agent 提供的素材数量。采集 MeshInstance3D、MultiMeshInstance3D、材质表面数、实例数、来源资源、包围盒、相机与碰撞结构；相机外对象也进入清单。普通 UI/2D 反馈原有上限保留，新增 3D 清单独立采集。
3. 技术门槛核对所有观察到的几何对象，而非只看最后一帧。未登记对象、资源不符、缺网格/材质、缺碰撞、未访问声明场景、静止重复截图、缺交互反馈均要求补齐。第一人称视点不强制制造不需要的第三人称人物外观，但必须存在活动相机和实体角色。
4. 至少两个通过实际移动/主操作得到的变化相机视角；同一画面包含玩家或第一人称视点、地形、交互物及 HUD。玩家必须与每个声明为实体的地形/交互对象产生真实碰撞证据，接触地面不能替代机关碰撞。
5. 碰撞探针保留最多 1.5 秒的真实接触事件。事件需发生在对应步骤内，防止松开按键后漏判，也避免重复使用上一步的接触。交互前后由真实输入改变已有游戏状态，不能用自报通过字段代替。
6. 3D 样板门槛在内容扩展前执行，遵循累计预算和有界修复；技术检查通过后仍进入独立只读截图审查。最终交付重新采样全部声明场景，并再次由 Reviewer 复核最新证据。样板阶段不要求尚未扩展的全部游戏结局；完整交付仍执行原有目标/失败/重开检查。
7. 采用已选方案中的 2D/3D 维度决定检查，避免标题没写“3D”便跳过门槛。Godot 检查工具同时返回场景缺口，不能在视觉检查失败时声称整体检查成功。
8. 场景结果保存在同一冻结构建的宿主报告中，并在「体验评测」显示「3D 场景检查」。覆盖统计与具体问题、画面审查重点分开；没有美术综合分，也不把自动核对通过作为用户验收。
9. 阶段 07 和总规划已改为用户确认的图片参考 → Three.js → GLB → Godot 路线；阶段入口和状态表同步已有专项，不再笼统把已有实现记作从未开始。未将任何未验收阶段改为“已验收”。

## 用户验收步骤

本地构建在 `<Noobi 工作树>`，未提交或推送。旧应用没有自动切换到新代码。检查结束时旧应用无运行中制作任务，但本轮没有重启它。

关闭旧应用后，在该工作树启动：

```sh
export PATH="$PWD/.noobi-private/runtime/node_modules/.bin:$PATH"
node_modules/.bin/electron .
```

1. 打开 Godot 3D 验收项目，执行体验评测，在报告中查看「3D 场景检查」。已有项目若缺场景规格，应明确报告缺失，不应直接显示已通过。
2. 按原方案继续制作时，观察「画面样板」步骤。Noobi 应先补充场景规格、代表性场景和实际操作证据，经独立审查后才扩展内容；完整交付仍重新检查。
3. 在专用验收副本中添加一个没有登记的场景网格，再评测，应能定位该对象；只增加素材账本记录不能消除问题。
4. 删除实体机关的碰撞或缺少真实接触步骤，再评测，应显示对应缺口。地面接触不能替代机关的证据。
5. 检查界面是否区分自动覆盖通过与画面审查。即便对象全部登记，明显占位美术仍应由独立 Reviewer 退回；不要把模型数量或“自动核对通过”当成最终游戏质量结论。

无需模型额度的隔离验证：

```sh
node_modules/.bin/electron scripts/scene-quality-smoke.mjs
```

脚本创建临时工程，使用真实引擎与隐藏浏览器操作，结束后清理临时数据，保留检查结果与截图。用户游戏不参与此测试。

## 本阶段边界和后续

- 当前支持 Godot 3D 主制作链。Web Three.js 游戏运行时没有接入此清单；已有 Web 基础评测不等于通过本专项。
- “全场景”在本实现中指全部已声明场景和本次运行中实际加载的几何。未访问的声明场景失败；未声明、未加载的隐藏关卡仍需根据原需求由 Reviewer 核对，不能声称凭运行清单发现所有未来内容。
- 单次采样最多 600 个相关 3D 节点、8000 个遍历节点、64 个角色体及 512 条近期接触记录；包体预算 240 KB。超限标为不完整，不当作覆盖通过。大地图多旅程分页汇总尚未实现；仍受现有 24 步/180 秒旅程限制。
- 本轮支持 MeshInstance3D 与 MultiMeshInstance3D 的网格/材质核对。其他特殊渲染节点缺少可核对的表面时报告待补齐，不能假装支持。MultiMesh 按实例组登记，实例数另留在运行证据中，不把节点数冒充唯一模型数。
- 相机视锥与包围盒不证明像素级可见性或没有遮挡。碰撞结构和实际接触不证明全地图永不穿模，也不验证所有模型尺寸、动画、性能或导航规则；这些仍需后续专项与实际试玩。
- 本轮没有自动美化用户游戏、替换现有占位模型、完成自然地形和植被美术，也没有完成截图/视频理解产品入口。
- 独立模型 Reviewer 的审美判断仍可能误判。新增调度路径已通过受控响应测试和开发者截图检查，但本轮未消耗模型额度进行真实 Reviewer 全链路试验；最终美术质量仍等待真实生成作品与用户验收。

实现依据：Godot 官方 [Camera3D 视锥与相机](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)、[MeshInstance3D 网格与材质](https://docs.godotengine.org/en/stable/classes/class_meshinstance3d.html)、[CharacterBody3D 碰撞反馈](https://docs.godotengine.org/en/stable/classes/class_characterbody3d.html)。运行行为另由上述真实引擎样例核验。

本轮为平台检查机制交付，等待用户验收；整体 Noobi 产品与完整游戏品质目标仍未完成。
