# 整场景品质与玩家体验复查

日期：2026-09-25。结论：当前游戏的整体产品验收不通过。前一轮灯笼专项的技术通过仍有效，但不能据此认定整场景建模、美术、玩法深度或生成效率达标。

## 本轮实际操作

通过 Noobi 现有游戏预览发送真实键盘输入，从暂停的工坊继续；读取界面目标后转动齿轮、观察机关反馈与升桥，移动、跳跃并走到桥头，最后暂停游戏。没有改写坐标、分数、生命或存档来制造结果。能源保持 6，生命保持 3，机关修复由 E 输入完成。

本轮只实际体验了工坊局部，不能声称完整玩过三个区域或完成长期游玩验收。截图保存在工作树 `.noobi-private/player-audit/`：

## 建模覆盖核查

`scripts/asset_catalog.gd` 的 18 个实际 GLB 绑定中，6 个走图片参考路线，12 个仍带有 `threejs-fallback` 元数据。这是模型绑定种类统计，不是屏幕面积或视觉完成度比例。

图片参考路线包含风车、齿轮、桥及三个灯笼变体。其余包括主角、守卫、滑翔翼、冲刺组件、能源晶体、三种岛屿装饰、星环机关、灯塔、记录与奖励箱。

此外，`scripts/main.gd::_build_world()` 直接以 cylinder/box 创建主要岛体、道路、森林树木、工坊箱体和遗迹柱子。这些大面积可见对象不在上述 18 个 GLB 的统计中。只检查 GLB 文件存在，或只统计新道具数量，会遗漏占据画面主体的灰盒内容。

产品标准应检查主要轮廓、部件、材质、尺度、动画和场景使用效果。程序化建模本身可以产生成品；问题在于通用占位外形未经视觉复核就被当成最终素材。

## 后续开发标准调整

### 1. 先交付一个完整场景样板

选择森林入口到第一机关与桥梁这一段，把主角、守卫、地形、树木岩石、道路、机关、拾取物、照明和 UI 作为一个整体制作。先确定游戏镜头下的场景参考和资产清单，再按统一风格生产；不要继续仅增加某个道具的多个变体。

验收：清单中主要可见对象没有未声明占位素材；从开局、正常行走、交互和转动镜头四类视角检查；文字不遮挡角色/机关；比例、材质与光照一致。完整场景截图由用户确认后再扩展其他区域。某项能力不足应明确标记未完成，不能自动用模板代替成品。

### 2. 同步缩短局部迭代的等待

先校验素材工单和试玩脚本，再进入昂贵执行；模型独立预览合格后批量集成；同一源码快照复用已通过的构建；局部道具变化先做对应检查，完整交付时跑一次全流程；仅因新失败或相关代码改变而重跑。独立素材可以并发，但集成和交付要在一致快照上验证。

验收：记录各阶段开始/结束、执行次数和返工原因；与本次同规模任务比较耗时；同一未变化快照不重复完整构建；发现真实失败仍阻止交付。不承诺尚未测得的固定分钟数。

### 3. 增加根据画面和反馈作决定的玩家体验验收

预设路线保留为回归工具，另做实际操作：读屏决定去哪里、尝试交互、走错路、跳跃、转镜头、跌落恢复、暂停继续，记录具体操作与结果。技术检查关注运行正确性；体验检查关注看得懂、操作顺畅、目标明确、选择与反馈是否有意义。

验收：保留连续操作证据及问题清单，修复后检查问题是否消失；不能用非空截图、像素变化或状态断言替代视觉与玩法判断；不能把几分钟切片认定为完整 30–45 分钟游戏。

本轮仅完成复查与标准纠偏，尚未重做全场景，也未实现调度加速。
