日期：2026-09-26。状态：开发者自验完成，待用户验收。基线：`0ad9d31`。按用户授权连续开发，人工验收独立保留。

沿用 03-D01–D04、03-A01–A04。先让上传图片实际进入规划协议，再打通可编辑理解、制作和同构建评审。不能用附件数量、文件路径或文字转述冒充已经看图。

## 界面方向（ui-design）

1. 面向用图片描述游戏的创作者，让用户指定借鉴哪一部分。
2. 语气直接、温和；继续使用现有米白面板、深色文字和暖色操作按钮。
3. 首页参考卡与方案对话框的理解卡分层，上传、选择用途、纠正理解依次呈现。
4. 复用产品正文排版，只有原有品牌标题保留像素字体。
5. 图片保持原比例，字段用清晰边界分组，错误就地显示。
6. 不增加装饰动画；加载、保存与校验用实际状态反馈。
7. 以“可见事实 / 玩法推断 / 尚不确定”三类信息作为理解卡的主要特征，保留图片来源。

沿用 React/Vite/Electron，不引入 Next.js。无需外部组件灵感搜索。

## 验证计划

- 图片签名、解码、尺寸、单张/总量、伪装格式、缓存篡改与越界 ID。
- 规划实际发送 localImage，模型不支持或加载失败时可见失败，不退回纯文字。
- 事实可追溯图片，用户修正版本持久化，后续方案使用修正内容。
- 参考图与生成素材账本隔离；制作/评审传入真实图片并关联构建证据。
- 五组图片理解与黑屏/遮挡对照另行实测；未运行前不标完成。

03-D01–D04 已实现：独立参考库、真实图像协议、可编辑理解卡、制作参考及当前 Godot 构建的截图证据。上传不会登记为已生成生产素材。规范化图片保存为稳定哈希 ID，启动制作时导出到工程 `references/visual`；模型回合实际携带 `localImage`。

## 运行及用户验收

当前阶段工作树使用 `codex/stage-01-plan-selection`。安装依赖后 `npm run dev`；也可 `npm run build` 后运行 Electron。开发实例与原应用分开，避免在旧运行进程验收新代码。

1. 首页点击「添加游戏参考图」，上传两张 PNG/JPEG/WebP，分别选美术风格、游戏界面，输入想做的游戏并生成方案。
2. 对照缩略图检查“可见事实 / 玩法推断 / 尚不确定”，点击「修正理解」，保存后校验。
3. 检查两套方案采用修正，关闭重开应用后从已保存的方案找回。选择路线再开始；规划不会提前制作游戏。

## 边界

截图不证明完整玩法，不保证模型理解无误或成品相似度。视频、局部裁剪与参考强度调节未在此阶段完成。直接绑定构建截图的新增能力覆盖 Godot；Web 仍沿用已有宿主试玩和查看图片流程。当前仍有章鱼样板美术未过关，详见报告 11。

格式实测曾发现 macOS nativeImage 不支持 WebP；现使用无网络、无 Node 权限的沙箱 Chromium 解码并转换为规范化 PNG，预先限制像素和体积，超时销毁窗口。原生三格式回归确认修复。
