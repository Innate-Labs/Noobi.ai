# Noobi：完整单人 3D 游戏生成开发规划

日期：2026-09-25。状态：已进入阶段化研发；阶段 00 已自验，待用户验收，后续能力仍是规划。本规划依据用户提供的《Noobi-AI游戏调研资料包》、当前本地代码和已有实测记录。以下数量、周期及质量阈值均为规划目标，不是已实现能力或成功率承诺。

执行入口：[分阶段开发与验收计划](development-plan/README.md)。研发按阶段交付，由用户验收通过后进入下一阶段；Noobi 产品内部仍在用户选定方案后自动制作。

## 1. 产品目标与范围

让不会使用游戏引擎的用户，通过想法、视觉参考、玩法偏好和制作预算，获得一个能直接启动、有连贯流程、有明确结束条件、支持继续游玩的完整单人 3D 游戏。用户也可以在已有作品上继续改规则、扩关卡和调整风格。

第一阶段支持：风格化第三人称探索、轻战斗、机关、任务、能力成长。第一款成品目标为 30–60 分钟的完整体验；用真人实际游玩验证，不通过重复敌人、冗长步行和强制等待凑时长。

后续顺序：同基础上的 3D Roguelite → 探索与轻生存 → 其他经过单独评测的品类。不在首版承诺任意品类、开放世界、联网多人、复杂载具、写实角色、完整配音剧情或 AAA 制作质量。这些请求进入能力评估，给出具体范围与额外投入，不静默缩减用户要求。

默认面向桌面键鼠，首选现有 macOS 开发环境，再增加 Windows 干净环境验收。浏览器分享是独立交付档位，创建项目时就确定兼容性和性能约束。

## 2. 当前基础与必须先解决的问题

当前本地分支 HEAD 为 a83ab31，远端主线引用为 ccc273e。两者不是同一完整版本：本地提交包括生产与质量增强；主线包含社区工作流改进及 David 的三个修复。开发起点必须先建立整合基线，不能让后续设计只存在于某条开发分支。

已见本地能力：
- Electron 桌面宿主、Codex App Server、规划/实现/评审流程。
- Godot 构建、Web 导出和实际输入试玩。
- 核心玩法阶段、构建指纹与冻结快照、生产检查点。
- Godot Implementer 回合内调用 noobi_godot_check。
- 素材账本、来源证明、程序化 GLB 和外部供应商网关入口。
- 运行状态探针及胜利、负反馈、重开证据检查。

仍需补齐或验证：
- startTurn 没有直接图片输入，不能保证截图实际进入模型视觉上下文。
- supportsVisualSample 仅覆盖 2D 平台游戏。
- 当前质量规格对多种玩法有文字要求，但不等于具备成熟的对应玩法组件和测试。
- ProductionCheckpointStore 保存通过阶段的构建指针，不等于完整任务恢复、项目版本回退或上下文记忆。
- 当前试玩单次上限 180 秒，不能据此证明 30–60 分钟流程完整。
- 3D 供应商仍为通用网关入口，缺少完整的原生异步生产、重拓扑、绑定与动画验收。
- 现有开发试验有未完成自主交付的记录，单元测试数量不能代表成品生成成功率。

## 3. 用户体验

1. 输入想法，上传参考图；可选类型、体验规模、目标设备和预算。
2. 每次用户发起制作或修改，先展示可选择、可编辑的方案：新游戏通常提供 2–3 套有实质区别的方案，小改动提供一套明确变更方案即可；用户也可上传或填写自己的计划。用户选择并点击开始后执行。方案包含核心循环、玩法系统、区域、风格、交付方式和预算区间。
3. 自动制作：灰盒 → 样板关卡 → 内容扩展 → 打磨 → 交付。用户可以查看当前可玩版本，默认不必逐阶段批准。
4. 显示真实阶段与结果：已完成内容、已知问题、当前可玩版本、累计消耗。避免用单一百分比暗示整体品质。
5. 完成后点击“开始游戏”。玩家不需要登录生成模型、配置供应商密钥或安装 Godot 编辑器。
6. 用户提出修改时，先列出受影响内容，再局部修改并回归；可以恢复上一可玩版本。新增游戏版本需声明旧存档是否兼容。

默认完整作品不依赖游戏过程中持续调用大模型。可选的生成式 NPC 对话以后增加，并提供成本、延迟与离线降级设计。

每项需求都有稳定 ID，并映射到实现任务、相关场景、测试、运行证据和交付状态。类型与文件名是设计建议，不要求一次建立庞大框架。

## 5. 六条研发主线

### A. 可组合的 3D 游戏基础

优先组件：
- 第三人称角色移动、坡道、台阶、跳跃及动画状态。
- 跟随镜头、避障、锁定/解锁、鼠标与手柄输入抽象。
- 交互、拾取、机关、门、检查点。
- 生命、伤害、攻击窗口、敌人感知与导航。
- 背包、任务、能力解锁、存档、暂停和设置。

按依赖逐项提供稳定接口，固定更新、数据定义与事件约定。自动化覆盖系统组合，而不只验证各组件独立运行。例如：任务给钥匙 → 背包记录 → 开门消耗 → 保存 → 重启恢复。

组件定义可更换参数、组合点和扩展接口，保留 AI 创造独特规则的空间。新品机制先在小场景验证，再进入正式游戏。能力库按支持程度标记：稳定、试验、尚不支持。

### B. 关卡、成长和内容组织

将关卡设计提前到首个可玩样板阶段。先确定目标与区域连接，再放置地形和装饰。

LevelGraph 至少描述：入口/出口、区域连接、任务前置、钥匙与能力、敌人遭遇、奖励、恢复点与可选路径。验证规则检查连通、前置循环、无法取得的道具及不可恢复状态；实际输入试玩补充几何与操作可行性。

内容生产遵循：一种机制教学 → 安全练习 → 增加压力 → 与另一机制组合 → 最终挑战。每个新增区域须有玩法或决策差异。

模板引导系统完整度，但不强行给所有游戏加入战斗、背包或 Boss。具体必备系统由品类与已确认 GameSpec 决定。

### C. 风格一致且可运行的资产

起点采用经过整理、有使用权的基础素材包；AI 补充主角、特色敌人、标志建筑及主题变体。来源许可与可再分发信息随资产保存。

生产流程：参考图/风格板 → 资产规格 → 检索或生成 → 下载和校验 → 减面/贴图/尺度处理 → 骨架与动画适配 → 碰撞与挂点 → 引擎中实机验收。

先打通一个供应商完整闭环，再做第二家适配。异步任务保存远端任务 ID，支持重启后继续查询、取消、去重、限流和成本上限；下载结果及时入库，不能依赖临时链接。

资产规格至少包括：尺寸、轴向、枢轴、材质、贴图、三角面数、纹理内存、骨骼和动画、碰撞、武器/道具挂点。供应商声明仅作为输入，宿主必须核验。

Blender 首期只封装确实需要的整理、检查和转台渲染任务。角色动作优先复用经过验证的骨架与动画库；自动绑骨能力不泛化到动物和异形。

### D. 可持续的制作调度

将“实现回合＋最多几轮全局修复”扩展为持久化任务图：任务包含输入版本、依赖、产物、允许改动范围、验收方式、预算和重试策略。

阶段建议：规格冻结 → 灰盒 → 3D 样板 → 内容扩展 → 体验打磨 → 发布验收。阶段通过后保存可玩构建及证据，失败保留最后可玩版本。

先保持一个写入者，隔离素材生产等独立任务；确有吞吐瓶颈后再引入多写入者和合并机制。角色模型配置可以增加，但不能把更多角色当作质量提升的证据。

建立工件存储、任务状态、设计决策及失败记录四类持久化信息。恢复后核验代码与素材版本，不能拿旧截图证明新构建通过。按错误类型重试：网络失败等待、供应商任务恢复、规则错误局部修复、方向错误重新规划。

### E. 看图、操作与体验质量

把参考图、当前构建关键帧直接送入模型视觉输入，记录图片哈希、构建 ID、步骤和采集时间，确保评审收到的是正确版本的画面。

四层验证：
1. 静态与构建：脚本、资源引用、场景依赖和导出。
2. 规则与系统：伤害、任务、道具、存档等状态变化。
3. 真实操作：移动、瞄准、攻击、交互、通关、死亡、重开。
4. 玩家体验：画面、手感、节奏、难度与理解成本。

保留宿主权威评测。用于快速诊断的调试跳转不能当作实际通关证明。测试和最低需求不允许由修复 Agent 自行删除、改低或标记通过。

长流程采用独立场景回归＋跨区域流程＋从正常新游戏开始的完整运行。测试可从存档进入某场景以加速定位，但发布验收还必须验证正常进度、保存后重启和最终结局。

视觉模型负责发现遮挡、布局和风格差异；真人试玩负责校准手感和趣味，不能把模型打分等同于玩家满意度。

### F. 一键运行和可分享交付

为玩家提供独立启动入口：加载、全屏、键位说明、音量、图形档位、暂停、存档与失败恢复。生成账号和供应商密钥不进入游戏包。

桌面完整版与浏览器试玩共享设计和主要内容，但分别维护构建档位与验证矩阵。浏览器需单独验证资源路径、加载、音频启动、指针锁定、持久化及性能。桌面发布逐平台处理导出模板、签名/公证或系统提示、安装与更新。

冻结构建后执行交付检查，再发布同一份产物。发布是显式动作；预览不会自动公开用户内容。现阶段先支持本机直接启动和导出包，托管分享在后续加入。

## 6. 标杆游戏与推广验证

标杆：暂名“遗迹回响”，风格化单人第三人称探索冒险。

成品范围目标：
- 三个相连且具有不同挑战的区域；主路线与至少一条有价值的可选路线。
- 一组可靠角色控制与轻战斗；数种有行为差异的敌人和一个最终挑战。
- 两种能改变探索方式的能力、相应机关与奖励循环。
- 教学、目标提示、完整结局、死亡恢复、保存与继续、设置。
- 整体风格一致、中文可读、关键动作与声音反馈完整。

首个纵向切片只做一个代表性区域，包含一个敌人、一种机关、一项能力和保存/恢复；切片用于验证生产方法，不作为最终完整产品交付。

最终需用同一流程生成至少三个不同主题/布局/机制组合的作品，再用未参与调试的需求测试泛化。不能只展示一款人工打磨过的成功案例。

## 8. 指标与评测方法

核心指标：在明确支持的范围、时间和成本上限内，无人工编辑工程，交付可直接运行且通过完整验收的游戏比例。

两周基线阶段先固定 10 个需求，每个独立运行 3 次，共 30 次，记录模型版本、提示、配置、资产来源、耗时、消耗、重试次数、人工介入和失败原因。数量用于建立初始基线，不代表统计充分；将其中部分需求锁为留出集，增加陌生需求测试。合成素材与 mock 测试不能代替真实供应商全链路。

建议试运行发布门槛，基线完成后冻结：
- 支持范围内的自主完整交付率目标 ≥80%，报告分子/分母及各品类结果。
- 发布验收场景不得有阻止完成流程或造成存档丢失的已知严重问题。
- 在明确列出的参考设备和分辨率上，正常档位目标 60 FPS；记录帧耗时分布与长帧，不只报平均值。低性能设备可设独立 30 FPS 档位。
- 每个发布候选至少有一次完整新游戏流程、一次保存退出后继续、一次失败恢复及一次中断制作后的恢复验证。
- 8–12 名目标用户试玩标杆，记录无需讲解的上手情况、卡点、完成率和愿意继续玩的原因。这是探索性反馈，不当作总体用户结论。
- 记录每次成功与失败任务的真实成本；成功交付成本应包含失败与重试的支出。获得基线前不承诺“一小时/几元生成完整游戏”。

保存四类独立结论：运行可靠性、需求覆盖、美术一致性、玩家体验。不要合并为没有解释力的“品质 100 分”。

## 9. 首两周任务队列

时间仅作短周期计划，未完成验收则顺延，不保证两周内完成全部任务。

1. 建立统一分支基线，保留本地已有功能与社区修复；锁定模型、运行时、依赖和评测配置。
2. GameSpec v1：需求 ID、品类、系统、关卡目标、交付平台、预算、不可静默删减约束。
3. 多模态回合输入：参考图与构建截图直接传入；验证确实收到图像、路径合法、证据属于当前构建。
4. 3D 起点 v1：角色、相机、地形碰撞、一个交互目标、一个敌人；用真实操作验证。
5. 制作状态最小闭环：记录任务与资产任务 ID、保存样板构建；关闭应用后恢复，不重复生成已经完成的素材。
6. 3D 样板验收：走通目标、负反馈、重开、保存/继续；加入相机遮挡与碰撞失败样例。
7. 运行第一批固定需求，记录成功和失败，不通过手工补代码掩盖问题；据此调整 V2 的范围和工时。

Definition of Done：实现、必要测试、构建证据、真实运行验证、失败边界说明齐全；涉及用户能力时同步文档；未完成项显式记录。

## 10. 资源与排期

建议最低配置：两名覆盖 Electron/Agent 和 Godot 的核心工程师，配合游戏设计/技术美术及测试支持。单人开发时保留相同顺序，缩减同时支持的玩法、设备和资产类型。

条件性工作量估计：V0 约 0.5–1 周，V1 约 2–3 周，V2 约 4–6 周，V3 约 3–5 周；在上述人员配置和外部服务稳定条件下，首个可重复交付版本约 10–15 周，另预留约 20% 不确定性。两周基线后重估。它不是当前能力或交付日期承诺，也不包含任意品类支持。

优先投入玩法组件、3D 验证、任务恢复和资产一致性。暂停增加与成品生成关系较弱的装饰性 UI、吉祥物变体以及未经完整接入的新供应商数量。

## 11. 主要风险与处理

| 风险 | 可观察信号 | 应对 |
|---|---|---|
| 生成器只会同一套换皮 | 未见需求成功率显著下降 | 扩展接口与留出集；按失败增加组件，保留独特规则试验场 |
| 内容丰富但系统互相破坏 | 修战斗导致任务/存档回归 | 状态契约、依赖图、组合测试及最后可玩版本 |
| 外部资产能下载但不能游戏化 | 骨架、尺度、碰撞、性能不合格 | 资产规格和入库门槛；基础素材库回退；明确未完成要求 |
| 不断修复造成成本失控 | 相同错误重复、无进展 | 任务级预算、失败分类、无进展检测、暂停并保留可玩成果 |
| 测试通过但游戏不好玩 | 自动结果好，玩家不愿继续 | 真人试玩、节奏/难度指标、分开报告品质 |
| Web 与桌面差异 | 输入、音频、存档或性能异常 | 创建时锁定交付档位；分平台运行同一候选构建 |
| 演示成功但无人能复现 | 依赖作者环境或人工介入 | 干净环境启动、完整日志、独立运行、多需求基准 |

## 13. 新增核心入口：从游戏截图/片段生成同风格、同类玩法的游戏

### 产品目标与能力边界

输入为用户截图或游戏视频，以及用户明确希望保留、改变、增加的内容。输出为基于可观察风格和玩法制作的新游戏工程、可玩构建及参考对照报告。该入口复用前述制作与交付流程。

必须区分：截图中可直接看到的画面事实、视频中可直接看到的事件与状态变化、模型推测的隐藏规则、用户指定的新要求。单张截图不能证明操作方式、成长系统、敌人 AI 或胜负规则；片段不能证明未出现的关卡和完整剧情。目标是重建用户选定且证据充分的风格与核心玩法，未展示内容按用户需求设计，不能宣称恢复原游戏完整规则或源码。

### 用户体验

1. 上传图片或片段，填写“我想做什么”。视频可选择关注的时间范围。
2. 可选参考维度：整体风格、镜头、场景、角色比例、UI、核心玩法、动作节奏；支持“图 A 参考美术、视频 B 参考玩法”。
3. 系统生成可编辑的理解卡，并据此提供可选择的制作方案：看到了什么、准备保留什么、按用户需求改什么、哪些信息未确定。用户可直接选择方案开始，也可修改后开始；关键缺项在此处集中处理。
4. 先生成代表性可玩片段，并展示参考和实际画面。默认自动继续制作，用户也可中途纠正方向。
5. 成品交付同时说明已复现玩法、按需求新增内容及尚未达到的参考效果。

例：用户上传 45 秒第三人称战斗视频，要求保留镜头、翻滚和体力约束，改成森林探索并加入三处遗迹。系统需从片段提取镜头关系、动作事件与可见体力变化；建立第三人称移动、翻滚、体力、命中及敌人响应原型，再制作森林主题与多区域进度。视频未显示的任务、存档和数值属于新设计，应明确记录。

### 处理链路

参考入库 → 图片区域分析/视频分段与抽帧 → 视觉特征与事件时间轴 → 证据支持的规则假设 → 合并用户要求 → GameSpec/ArtBible/LevelGraph → 可玩样板 → 对照评审 → 内容扩展 → 正式交付。

### 建议模块与数据

- ReferenceMediaService：独立参考用途、图片和视频入库、元数据、时长/尺寸/大小限制、文件校验、缩略图和本地预处理。参考不自动成为生产素材。
- VideoPreprocessor：保留时间戳与音视频同步，镜头切分、关键帧提取、事件附近密集采样。低频均匀抽帧只用于初筛，不能支撑对短攻击窗口和瞬时反馈的判断。
- ReferenceAnalyzer：解析镜头、色彩、材质、场景结构、角色比例、UI，以及动作事件、状态变化和可见反馈。原生视频理解与带时间戳的帧序列作为可替换路线，以实测决定模型。
- ReferenceSpec：每个结论含来源文件、帧/时间范围、观察内容、推断、置信说明、用户覆盖值和对应需求 ID。置信度需通过评测校准，不能只相信模型自评分。
- MechanicHypotheses：记录操作、前提、事件、结果、约束及尚待确认信息。视频中角色移动不直接证明使用某个按键；血条变化也不直接证明精确伤害公式。
- ReferenceComparison：在相近视角、状态和动作阶段采集生成游戏证据，分别比较风格、空间与镜头、动作反馈、规则行为，输出可执行修改项。

摄像机运动与物体运动需要分开解释。剪辑、慢放、回放、过场和宣传片应单独标记，不把其中展示全部认定为可操作玩法。单视角无法确定背面几何和完整关卡拓扑，补建内容保持明确假设。

多份参考冲突时，采用用户对各参考的用途指定；用户明确文字要求优先于模型推断。上传内容、OCR 文本和字幕都是待分析数据，不作为系统指令执行。

### 与现有工程的关系

已确认当前项目参考文件只允许 PDF/MD/TXT/JSON/CSV；首页图片被导入素材，尚无完整的视频分析入口；startTurn 缺少直接图片输入；3D 生成工具没有参考图参数。因此不能只新增上传按钮。

优先修改 reference 入库和共享契约，增加直接视觉输入；随后引入 ReferenceSpec，将其接入 Planner、素材规格和 Reviewer。原有制作、构建、试玩与版本服务继续复用。

### 分期与验收

R1，截图参考：先支持 1–5 张图和文字要求，提取风格、镜头、场景/UI结构；用户文字补充核心玩法。多张图的用途可区分，样板画面可逐项对照。

R2，短视频玩法参考：建议首期限定 30–120 秒实际游戏片段，可裁剪关注段。支持事件时间轴、核心操作循环、镜头变化和可见状态约束，并输出带时间戳的证据与未知项。限制是产品范围建议，不是模型接口限制。

R3，完整作品扩展：将参考片段中的玩法系统复用于新的关卡、成长与内容；验证跨区域、存读档和正常通关。片段还原成功不等于完整作品成功。

R4，多来源混合与精细对照：不同参考分别控制风格、镜头、玩法和节奏；通过版本对比和用户反馈调整。

纳入原路线：R1 进入 V1，R2 与 V2 配套，R3 是 V2/V3 的成品验收部分，R4 后置。排期需在首批分析与样板实验后重新估算，不能假设新增视频能力不增加原项目工作量。

评测采用有已知规则与操作记录的自有/授权测试片段：测事实提取正确性、关键事件召回、无依据规则断言、用户纠正量；再测真实生成游戏的核心机制和风格对齐。设置静态图、正常游玩、含剪辑视频、UI遮挡、多份冲突参考等样本。禁止以图像相似度或一段相似录像替代实际交互规则验证。

技术可行性参考：视频理解 API 已支持描述、分段、提取信息和按时间戳问答，但这不证明能直接逆向恢复完整游戏。官方文档：https://ai.google.dev/gemini-api/docs/video-understanding


## 14. 制作前的方案选择与用户编辑（产品流程更新）

### 核心决策

每次用户主动发起新游戏制作、功能扩展或内容修改，都先进入方案阶段。Noobi 根据文字、参考素材和现有项目生成方案，用户选择或编辑后点击开始。用户自己的计划也作为一等输入；系统整理和检查它，保留用户明确要求，不强制改写为系统推荐方案。

“每次开发”指用户发起的一轮制作请求，不包括已经选定方案内的内部实现步骤、测试和自动修复。一次确认后，系统按方案持续推进；超出选定范围或预算上限时，暂停受影响任务并提出补充方案。

### 方案数量与差异

新项目默认 2–3 套，推荐方案优先；小修改只提供一套清晰方案，不为了凑选项制造差异。所有方案满足用户明确的不可变要求，例如用户要求 3D 时，不以 2D 替代作为默认降级方案。

可比较维度：核心玩法重心、内容规模、风格实现、交付平台、制作复杂度、预估时间/成本及不确定性。差异必须体现在玩家体验和制作范围上，不只更换名称或主题。

示例：用户要求参考视频制作森林遗迹 3D 游戏，可提供探索解谜、轻战斗成长、关卡式挑战三种方案；如果用户已经明确必须保留战斗，则所有方案都保留该要求，在探索深度、战斗内容和关卡组织上区别。

### 方案呈现与编辑

方案卡展示：一句话玩法、保留的参考特征、主要系统与内容、交付方式、预计制作区间、关键假设及限制。展开后可查看阶段目标与验收要求；工程实现细节默认收起。

支持三种编辑方式：
- 自然语言：例如“保留 A 的战斗，加上 B 的探索，关卡改成三关”。
- 结构化字段：镜头、角色、战斗、任务、区域数量、成长、风格、存档、操作设备、交付平台与预算。
- 自带计划：粘贴或上传用户自己的设计文档，系统转换成可执行方案并标出缺项。

多个方案的内容可以组合，但合并后必须检查系统依赖和预算。用户编辑会生成新版本，并显示受影响的内容；手动修改字段不得在重新生成方案时被静默覆盖。对不可同时满足的约束给出具体冲突及可选调整，不把未解决冲突藏进制作过程。

参考分析中的“观察事实”“推测规则”“用户指定”保持分离。用户明确指定覆盖模型推测；视频中未出现的规则不伪装成已识别事实。

### 开始执行与版本

点击“按此方案开始制作”时，宿主冻结 planVersion、需求 ID、参考版本、交付目标、验收标准及预算上限。将选定方案映射为 GameSpec、ArtBible、LevelGraph 和任务图。

最小状态流：草稿 → 可执行 → 用户选定 → 制作中 → 验证中 → 完成；另有等待用户、外部阻塞、已停止。草稿不触发实际游戏制作或付费资产生成；若方案分析本身调用外部模型，其成本应计入累计消耗。

PlanStore 保存方案列表、用户编辑、选定版本、估算依据及关联运行。每次运行绑定不可变方案快照；执行过程中编辑形成下一版本，不悄悄改变正在运行的验收要求。

### 已有游戏的迭代

用户提出修改后，系统对当前可玩版本生成变更方案：本轮改什么、哪些系统受影响、哪些验收要重跑、存档是否兼容。用户选定后，只对该范围展开实现与回归。

用户在制作中改变需求时，先展示差异与成本影响，并选择在安全检查点切换或完成当前阶段后再开始新计划。最后可玩版本始终可访问；恢复游戏版本时，同时恢复对应设计与资产引用。

### 实施顺序

P1：方案数据结构、方案卡、2–3 套备选、选定后开始；先接入现有文字创建流程。
P2：自然语言及字段编辑、自带计划、差异展示、选定版本持久化与恢复。
P3：图片/视频分析产物进入方案，支持按维度引用和多方案组合。
P4：已有项目的增量变更方案、预算更新、制作中需求变更与版本切换。

这些任务与 V1 的 GameSpec/制作调度共同建设；不先独立做大型可视化编辑器。

### 验收

- 未选择方案并点击开始时，不创建实际制作运行或发起付费素材任务。
- 开始执行的版本与用户最后看到并选定的版本一致；防止编辑保存与开始按钮之间的竞态。
- 用户编辑、刷新和重启后内容仍保留；重生成不会覆盖锁定字段。
- 方案冲突、关键缺项或预算超限能在执行前呈现。
- 多个备选满足共同必需需求，并有实质、可解释的差异。
- 用户的小改动不会触发无关系统重写；回归包含受影响功能和原有关键流程。
- 自动测试与修复在已确认范围内持续执行，不把内部修复循环变成重复审批。
