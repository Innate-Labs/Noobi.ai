# Noobi.ai 项目宪章

## 核心原则

### I. 产品事实与品牌一致性

所有新增的用户可见名称和文案都**必须**使用 **Noobi.ai**。产品能力声明**必须**由当前代码
和可重复的验证结果支持；规划中的功能、目录条目和第三方集成都**不得**被描述为已经交付的
原生能力。

当前内置的游戏制作主线面向 Phaser 3 和 2D Web 游戏。Unity、Godot、Unreal Engine、
Blender 等工具**必须**被描述为可选连接，并明确依赖相应的 Skill、MCP Server、编辑器插件
和本机安装环境。已有内部兼容标识可以暂时保留，但前提是迁移方案能够保护现有项目、凭据、
应用身份和 IPC 使用方；这些内部标识**不得**出现在新增产品文案中。

### II. 桌面端信任边界

Electron 渲染进程（Renderer）**不得**直接访问 Node.js、文件系统、子进程或系统凭据。所有
特权操作**必须**通过满足最小权限原则的强类型 Preload API，并由可信的主进程服务执行。

每个特权 IPC 处理器都**必须**验证调用方、执行运行时输入校验、限制字符串与集合长度、约束
路径、协议和枚举值，并且只向渲染进程返回可安全公开的数据。远程内容、任意页面跳转和新增
WebView 类界面默认禁止，启用前**必须**完成专项安全审查。

### III. 本地优先数据与显式副作用

生成的游戏和素材**必须**保存在用户明确选择的目录中，并且能够脱离 Noobi.ai，独立通过
Finder、终端和常规版本控制工具使用。文件操作**必须**在解析规范路径后执行目录包含校验，
并拒绝目录穿越和不可信符号链接越界。

安装或更新依赖、删除 Skill、打开外部地址以及其他会改变系统状态的操作，都**必须**由用户
显式触发。依赖操作**必须**将固定标识映射到白名单命令和参数；禁止接受 Renderer 提供的
可执行文件名、包名或任意参数，也禁止使用 `shell: true`。

### IV. 可观察、可恢复的 Agent 执行

Agent 运行期间**必须**持续提供结构化的项目状态、制作阶段、工具调用、执行结果、错误和最终
状态。长任务**必须**可停止，并在能够安全恢复时保留 Session、现有素材和可恢复的项目状态。
无输出和超时**必须**转化为明确状态，不能表现为无限期进行中。

当前调度器在整个应用内只有一个执行槽位。在后台队列、隐藏并行 Agent 或多项目并发执行真正
实现并通过验证之前，文档和界面都**不得**声称支持这些能力。Agent 自动化可以写入项目文件并
运行命令；它**不得**被描述为零风险能力，也不得与渲染进程的 Chromium Sandbox 混为一谈。

### V. 凭据与插件零信任

API Key 以及 MCP 环境变量和请求头中的秘密值**必须**通过操作系统安全存储持久化，并通过
受控通道交给运行时。日志、事件历史、错误、遥测和开发者界面**必须**对秘密信息进行脱敏；
API 使用记录**不得**保存 API Key、提示词、接口地址 URL 或 MCP 秘密值。

所有 Skill、GitHub 仓库、MCP 服务端和编辑器插件都**必须**被视为不可信输入，精选条目也不
例外。安装界面**必须**展示来源、许可证、依赖要求和重要风险。每个 MCP 服务端都**必须**可
单独启用、禁用和设置信任状态；精选机制**不得**绕过输入校验或工具确认。本机 Token 和延迟
指标仅用于诊断，不代表服务商账单，也不构成标准化性能基准。

### VI. 兼容性变更必须包含迁移

共享类型、IPC 通道、持久化状态、项目元数据、Skill 位置、MCP 配置、凭据标识和 Electron
应用身份都属于兼容性契约。修改任何契约时，都**必须**提供旧数据读取或迁移逻辑、新字段的
已验证默认值、契约测试，以及对现有项目、会话和凭据的影响说明。

品牌清理可能影响安全存储身份、文件位置、包或 API 契约、应用更新时，**不得**通过无差别的
全局替换完成。历史标识**必须**通过明确的迁移方案逐步隔离和退役。

### VII. 证据先于交付

每项变更都**必须**完成与风险相匹配的验证。界面和独立逻辑变更需要聚焦测试，并通过桌面端
两个 TypeScript 配置的检查。IPC、持久化、路径和凭据变更需要主进程校验测试，以及迁移或
契约测试。Agent 或运行时变更需要覆盖停止、恢复、超时、流式事件和脱敏。插件与依赖变更
需要覆盖白名单、失败路径、缺少工具和用户确认。打包变更需要覆盖运行时依赖准备、冒烟测试
和安装包验证。

交付说明**必须**列出实际执行的验证和未执行的检查。“已支持”“已修复”或“生产可用”等结论
**必须**以证据为前提，不能用来替代验证。

## 工程约束

- 仓库**必须**继续使用 Node.js 20+、npm workspaces、ES Modules 和严格 TypeScript。
- 依赖方向**必须**保持为
  `Renderer -> Preload Bridge -> IPC -> Main Services -> Filesystem/Runtime`；任何层都
  不得绕过这条边界。
- 业务、网络、文件系统、进程和持久化逻辑**应当**放入职责单一、可注入、可测试的服务，不应
  持续堆积在 `main.ts` 或 React 界面中。
- `node_modules/`、`dist/`、`.runtime-deps/`、`.app`、DMG 和发布目录等生成依赖与
  发布产物**不得**进入源码提交。
- macOS DMG 是当前发行基线。开发构建**必须**与已经签名并完成公证的公开发行构建明确区分。
- 在更新器、可信发布源、完整性校验、回滚机制和干净机器测试完成之前，产品**不得**声称
  内置自动更新能力。

## 规格驱动工作流与质量门槛

功能开发**必须**遵循仓库内的 Spec Kit 流程：项目宪章 -> 功能规格 -> 必要时澄清 -> 实施计划
-> 任务列表 -> 跨产物分析 -> 实现。功能规格**必须**先描述用户结果和验收场景，再描述实现
细节。实施计划**必须**在调研前和设计后各执行一次项目宪章检查。

桌面端默认质量门槛为：

```bash
npm run typecheck --workspace=@gameagent/desktop
npm test --workspace=@gameagent/desktop
npm run build --workspace=@gameagent/desktop
```

影响共享工作区或运行时的变更，还**必须**执行相应的根级类型检查、测试和构建。安装包变更
还**必须**执行打包准备、运行时冒烟测试和 macOS 安装包验证。公开发行还**必须**独立验证
签名、公证、目标架构以及在干净机器上的安装。

## 治理

本项目宪章是所有 Noobi.ai Spec Kit 产物的最高治理依据。每份功能规格、实施计划和评审都
**必须**证明其符合本宪章。任何例外都需要书面记录适用范围、原因、风险、回滚路径、负责人和
到期条件；禁止没有记录的“临时”违规。

修订宪章时，**必须**提交修订说明，审查受影响的模板与产品文档，并在兼容性契约发生变化时
提供迁移方案。宪章版本遵循语义化版本：MAJOR 表示删除或重新定义核心原则，MINOR 表示新增
原则或实质扩大强制范围，PATCH 表示不改变义务的措辞澄清。文档与实际行为冲突时，已验证的
代码和测试是当前事实来源；不准确的产物**必须**在同一变更中修正，或被明确记录和跟踪。
